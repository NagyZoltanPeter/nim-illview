# illview — External Audit Review

*Date: 2026-07-27. Scope: read-only review of the repository at commit `febd604`.
Method: four independent review passes, one per aspect — (1) developer ease of
use, (2) ease of integration with other projects/backends (concrete target:
embedding as the TUI frontend of logos-delivery, a chronos-based daemon),
(3) composability, (4) model/view/control separation. Evidence is cited as
`file:line` against the audited commit. Companion document:
[AUDIT-IMPLEMENTATION-PLAN.md](AUDIT-IMPLEMENTATION-PLAN.md) with concrete
plans for every recommendation.*

---

## Executive summary

The architecture is genuinely strong for its stated goal — an embeddable,
zero-idle-cost TUI frontend for a chronos daemon — and better than typical TUI
frameworks on decoupling and testability. The weaknesses cluster at the
*maturity and packaging* layer, not the design layer: doc/code contradictions,
conventions that only work single-module, missing safety rails in the DSL
macros, and a lifecycle footgun (dispose + ORC churn) that every audit aspect
ran into independently.

Four independent review passes converged on the same three hotspots, which is
a strong signal these are the first things a real external adopter will hit:

1. **The `emits:` context documentation bug** — REFERENCE.md says semantic
   events fire on the *default* ctx; code, cookbook, and tests say *session*
   ctx. A model listener written from the reference silently never fires.
2. **The dispose / ORC-churn lifecycle footgun** — the framework mandates
   `--mm:orc`, yet the natural "build a window per click" pattern hits a
   documented deterministic cycle-collector SIGSEGV; the required
   build-once/add-remove pattern is buried in a deviations doc and example
   comments.
3. **Silent DSL fallbacks** — the generic `createView` fallback bypasses
   widget constructors, and the `on:` handler resolution silently downgrades a
   mistyped payload handler to the payload-less variant.

## Strengths (keep and advertise)

- **Event-loop cohabitation is the framework's best asset.** `app.run()` is an
  ordinary async proc (`src/illview/core/app.nim:298-306`) — it never owns the
  loop. Input is readiness-driven via `addReader2` on a dedicated tty fd
  (`src/illview/backend/driver_posix.nim:104-117`), rendering is dirty-driven
  and fps-capped, and an idle app has zero pending timers (measured 0.00 CPU).
  `enableTui`/`disableTui` (`app.nim:264-289`) give first-class, re-entrant
  attach/detach. This is exactly the right shape for embedding in a daemon.
- **The broker layer is a high-quality decoupling substrate.** Identity in the
  route, not the payload (`src/illview/vocab.nim:1-13`); ctx-as-plain-value
  handles that are safe after dispose (signals return `err`); no-echo setters;
  session-ctx sandboxing (`src/illview/core/view.nim:100-132`). A model really
  can drive widgets it never imports.
- **Headless testability is excellent.** 200+ terminal-free tests including
  pixel-exact render snapshots (`tests/test_render_snapshot.nim`), `StubBus`
  as the App default, real key/mouse dispatch in tests, README screenshots
  generated by the framework itself (`tools/screenshots.nim`).
- **Tiny dependency footprint** — chronos + brokers only, illwill vendored as
  a single file (`illview.nimble:12-14`), removing a whole class of version
  conflicts. The dedicated-tty-fd input driver avoids the classic
  O_NONBLOCK-on-fd-0 breakage of host stdout.
- **Nested declarative components work multi-level** with per-instance broker
  isolation proven by example (`examples/ex10_instance_ctx.nim`) and tests
  (`tests/test_mount.nim:56-96`), and layouts nest arbitrarily and cleanly.
- **Honest documentation culture** — deviations, gotchas, the deferred
  Windows driver design, and the logos-delivery consumption model are all
  written down.

## Aspect 1 — Developer ease of use

### Onboarding

- *Strength:* the minimal app is genuinely small (`README.md:43-69` is a
  complete ~25-line app) and the 14-example ladder is well graded, from raw
  input echo to a full MDI showcase.
- *Weakness:* user-facing docs leak internal build-plan jargon — "plan-2 D4",
  "deviation #15", "P22/D19" (`docs/REFERENCE.md:52,112,179,193,252,258`;
  `src/illview/dsl/pragmas.nim:29,34,66`). A new user must cross-read six
  internal design docs to decode the reference.
- *Weakness:* two learning curves are stacked — the pragma DSL (six wiring
  mechanisms on a single field, `docs/REFERENCE.md:35-53`) *and* the brokers
  event model (five bus tiers, three context scopes). The docs never say
  "start imperative, add the DSL later".
- *Weakness:* the install story is unverified and unversioned — install by raw
  git URL, no tags, no lock file, no CI; README contradicts itself (223 tests
  at `README.md:9,34` vs "106 tests" at `README.md:289`; "Nim ≥ 2.0" at
  `README.md:294` vs `nim >= 2.2.4` in `illview.nimble:14`).

### API ergonomics

- *Strength:* naming is consistent (`newX` constructors, `onX` slots, `setX`
  mutators); the `app.run()/stop()/requestRedraw()` surface is clean.
- *Weakness:* `{.gcsafe, raises: [].}` on every callback, plus user-side
  `{.cast(gcsafe).}` even in the framework's own examples
  (`examples/ex05_declarative.nim:20-22,83`); docs are inconsistent about when
  it is required (`docs/COOKBOOK.md:326-330` shows a bare proc).
- *Weakness:* dispose discipline is a real footgun — forgetting `dispose(v)`
  leaks under refc *and* orc (`docs/REFERENCE.md:185-198`,
  `src/illview/core/view.nim:317-335`); user-attached ctx listeners must be
  dropped *before* dispose "or the recycled ctx inherits them"
  (`docs/COOKBOOK.md:280-281`) — with no runtime detection.
- *Weakness:* the mandated ORC mode collides with a documented deterministic
  ORC SIGSEGV on window-churn patterns (`repro/README.md:3-17`); the
  workaround lives in deviation #22 and a showcase comment
  (`examples/ex13_showcase.nim:59-63`), not in README or the cookbook.

### DSL failure modes

- *Strength:* malformed pragma *shapes* produce targeted `error()` calls with
  node positions (`src/illview/dsl/mount.nim:269-271,290-291,300-301,330-335`;
  `src/illview/dsl/uievents.nim:130-131,158-160`).
- *Weakness:* names *inside* pragma strings are never validated —
  `bindValue: "userVla"` becomes a bare `ident` (`mount.nim:292-297`) and
  fails with a generic error at the `mount(T)` expansion site, not at the
  pragma line. The macro has the record list in hand and could suggest
  candidates.
- *Weakness:* `on:` handler resolution via `when compiles(...)`
  (`mount.nim:339-353`) silently downgrades a handler with a slightly wrong
  payload signature to the no-payload call.
- *Weakness:* the generic `createView` fallback (`mount.nim:366-368`) accepts
  *any* View subtype and constructs it with bare `T(); initView()`, bypassing
  `newTreeView`-style constructors — while `docs/REFERENCE.md:39` claims
  `child` works on "any widget". Half-initialized widgets at runtime, no
  warning.
- *Weakness:* `parseStmt`-generated code (`uievents.nim:120-123,162-168`) has
  no source mapping; type errors there surface with useless line info.

### Debuggability

- *Strength:* the logging-while-TUI-owns-the-terminal problem is squarely
  addressed (cookbook recipe 23; `examples/ex14_logpane.nim` + `.cfg`), and
  crash-time terminal restore (`app.nim:67-97`) plus `disableTui()/enableTui()`
  suspend/resume are better than most TUI frameworks offer.
- *Weakness:* no framework-native logging/tracing facility, no dispatch/event
  trace mode, and frame exceptions are silently swallowed
  (`app.nim:210-212`). No guidance for the "forgot `invalidate()`, screen
  silently stale" symptom.

### Testing story for app authors

- *Strength:* the framework dogfoods headless testing heavily (18 test files,
  cell-exact snapshots, `dispatchKey`/`dispatchMouse`, `StubBus` default).
- *Weakness:* snapshot testing is not a public capability —
  `tests/test_render_snapshot.nim:6` imports the vendored backend path, and
  the `render`/`rowStr`/`cellStr` helpers every UI test needs are private
  test-file code. App authors must copy internals to snapshot-test their own
  screens. Cookbook recipe 14 covers interaction testing but never render
  assertion.

### Tooling / packaging

- *Weakness:* no CI at all (the "tests 223 passing" badge is a static label);
  no `nim doc` task or hosted API docs; no releases, no `nimble.lock`,
  floating lower-bounded deps. README's examples table omits `ex14_logpane`.
- *Strength:* the nimble tasks that exist (`test`/`examples`/`screenshots`)
  are simple and work-shaped.

## Aspect 2 — Integration with other projects/backends (logos-delivery)

### Event-loop cohabitation — strong

- `app.run()` is `{.async.}`: `enableTui()` + `await quitFut` with
  `disableTui()` in `finally` (`app.nim:298-306`). The host daemon keeps
  running all its futures; a daemon can skip `run()` entirely and drive
  `enableTui`/`disableTui` directly — `docs/DESIGN.md:31-33` and deviation #9
  name logos-delivery as the intended consumption model.
- Zero idle cost is real: readiness-driven input, one-shot fps-capped frame
  task, no pending timers when idle (deviation #13). Under load, redraws
  coalesce (`renderPending` + `fpsCap`), so a busy daemon pays at most ~30
  cheap frames/s.
- Single-thread invariant is asserted, not just documented
  (`assertLoopThread`, `app.nim:164-172`).
- *Gap:* no `isatty` guard — `enableTui` in a non-tty daemon (systemd, piped
  logs) writes altscreen/mouse escapes into stdout
  (`illwill_vendored.nim:774-799`). No remote-attach story (tmux/screen is
  the workaround).

### Terminal & logging conflicts — workable, sharp edges

- Host stdout/stderr writes while the TUI is active corrupt the altscreen
  until next redraw. The chronicles dynamic-sink recipe
  (`examples/ex14_logpane.nim:28-42` + `.cfg`) is the right shape for a
  chronicles daemon but is an example, not an API; non-chronicles output
  (libp2p C-level prints, `debugEcho` from deps) has no capture story.
- **Signal-handler hygiene is the riskiest area for a host:**
  - SIGWINCH: restored to `SIG_DFL`, not the *previous* handler, on stop
    (`driver_posix.nim:116,124`).
  - SIGSEGV/ABRT/BUS/ILL/FPE: `installCrashRestore` (`app.nim:73-97`)
    permanently overwrites prior handlers — fights a host's
    libbacktrace/crash-dump machinery (`-d:noCrashRestore` exists but is
    obscure).
  - SIGTSTP/SIGCONT: installed in `consoleInit`
    (`illwill_vendored.nim:602-604`), never removed in `consoleDeinit`.
  - SIGINT/SIGTERM: untouched — good (the daemon's handling keeps working),
    but if the host exits without calling `disableTui`, the operator's
    terminal is left in altscreen + mouse-tracking mode; crash restore does
    not cover INT/TERM.

### Data ingestion — good architecture, single-thread only

- Three well-layered tiers: string-topic domain bus
  (`src/illview/core/bus.nim:44-69`, `src/illview/bus_brokers.nim:25-54`),
  typed broker events + instance-ctx signals (the strong path), and direct
  mutation with `invalidate()` auto-scheduling a frame
  (`view.nim:268-272`, `app.nim:122-123`).
- The string bus is positioned as the observability tier; its real cost is
  that a NetViz-style feed forces the daemon to pre-format payloads into
  display strings, losing structure for later filtering.
- Thread-safety: none, by design (single-thread EventBroker mode,
  `bus_brokers.nim:3-6`). Fine for a chronos+libp2p daemon, but there is no
  documented `ThreadSignalPtr`-style marshaling recipe for hosts with worker
  threads (db, crypto, archive).

### Dependencies, platform, headless

- Light footprint; but the Nim floor contradiction (`>= 2.2.4` vs docs
  "≥ 2.0") will bite pinned toolchains, `brokers` is not in the status-im
  vendored ecosystem, and there is no tag to pin. The orc requirement is
  stated imprecisely (REFERENCE claims identical behavior under refc).
- POSIX-only is honest and acceptable for an opt-in operator UI — headless
  operation still works on Windows, only `enableTui` fails
  (`driver_fallback.nim:21-24`); `docs/WINDOWS-DRIVER.md` is a credible
  deferred plan.
- Headless renderability is better than typical: widgets draw through
  `DrawContext` into a `TerminalBuffer`; `display()` happens only in
  `app.frame()`. Practically decoupled — but not formally abstracted (no
  render-target interface; types come from the vendored illwill).

## Aspect 3 — Composability

### Component model

- *Strength:* nested `{.view.}` components are first-class and recurse
  multi-level (`mount.nim:224-232`; `examples/ex05_declarative.nim:28-46`
  shows three levels); macro internals are hygienic (`genSym`,
  `mount.nim:164-165`); base type is flexible (Group, Window, GroupBox).
- *Weakness:* **no pragma/field inheritance** — `mount` reads only the type's
  own `recList` (`mount.nim:161,214`); a `{.view.}` type inheriting another
  silently ignores the base's `{.child.}` fields. No error, no doc.
- *Weakness:* **cross-module reuse is fragile** — handlers are bound as raw
  `ident(...)` at the *expansion site* (`mount.nim:302,337`), so mounting a
  component from another module requires exporting and importing every
  handler where the outer screen mounts. The factory-proc workaround
  (`proc newFormPane*(): FormPane = mount(FormPane)`) is documented nowhere;
  all examples are single-module.
- *Weakness:* `uiEvents(T)` is a separate, forgettable top-level call, and
  its generated event types can collide (two components using
  `emits: "Changed"` in one module) or become ambiguous overloads across
  modules.
- *Weakness:* no declarative size hints — only `stretch` (both axes,
  `mount.nim:39-41`); `ex10_instance_ctx.nim:69-70` must patch hints
  imperatively after mount.

### Custom widgets

- *Strength:* the contract is small — `ref object of View` + `initView` +
  override `draw`/`measure`/`arrange`/`handleEvent` (`view.nim:115-226`);
  parent-owned decoration means content-local coordinates for free; a
  complete custom widget fits in ~14 lines (`ex13_showcase.nim:42-55`).
- *Weakness:* the contract lives only in `view.nim` doc comments — no
  "writing a widget" chapter. DSL integration points (`createView`,
  `bindSlot`, `bindValueSlot`, `widgetValue`, `setCaption` overloads,
  `mount.nim:14-77`) are an undocumented extension surface, and the generic
  `createView` fallback silently bypasses custom constructors.
- *Weakness:* `uiEvents` payload mapping is keyed on the **type-name string**
  (`uievents.nim:51-63`) — custom widgets cannot declare a value type for
  `emits:`/`bindValue`, and a user type coincidentally named `Input` would be
  mis-classified.
- *Weakness:* the theme vocabulary is closed — `ThemeToken` is a fixed enum
  backing `array[ThemeToken, Style]` (`theme.nim:18-46`); custom widgets
  cannot add a token, there is no theme derivation helper, and
  `effectiveTheme` picks the nearest theme wholesale with no per-token
  fallback (`view.nim:154-160`).

### Multi-instance & lifecycle

- *Strength:* per-instance isolation is deliberate and proven — unique
  `brokerCtx` per view (`view.nim:119`), per-widget-ctx `on:` listeners,
  zero cross-talk between two mounts of one form (`ex10_instance_ctx.nim`).
- *Weakness:* `emits:` events are session-scoped; with two instances a model
  listener discriminates only via raw `senderId: int` — no id→view helper.
- *Weakness:* `bindRequest` providers are global per event type
  (`uievents.nim:142-145`) — per-instance validation is impossible; last
  `replaceProvider` wins for all instances.
- *Weakness:* instance ctx ids are never reclaimed (`view.nim:326-329`,
  16-bit space) and dynamic churn is additionally landmined by the ORC crash
  — forcing the build-once/add-remove pattern and capping
  "many screens on demand" scalability.
- *Weakness:* doc drift — `docs/REFERENCE.md:190` claims dispose calls
  `releaseInstanceCtx` (it does not), and `REFERENCE.md:47,162` say `emits:`
  fires on the default ctx (it fires on the session ctx,
  `uievents.nim:120-123`).

### Screens / navigation

- There is no screen/page/navigation concept — only Desktop + windows +
  the modal stack (`app.nim:155-160`, `routing.nim:5-7`). A dozens-of-views
  app must hand-roll a named-window cache with activate-or-open (the ~40-line
  `exCache` pattern in `ex13_showcase.nim:59-186`), and eager prebuild is
  effectively *required* for safety. Tab traversal is scope-global
  (`routing.nim:41-56`) — no per-window focus trap short of a modal.

### Layout

- *Strength:* layouts nest arbitrarily (all containers are `Group`
  subclasses); `measure` aggregates bottom-up through `outerHints` so
  borders/padding compose correctly.
- *Gaps:* no spacer/flexible-glue widget (the idiom is a stretchy empty
  Label, undocumented); no grid cell spanning; no wrap/flow layout; `stretch:`
  is both-axes-only; no per-child margin or justify/gravity for leftover
  space.

## Aspect 4 — Model / view / control separation

### Where state lives

- The declarative form is a deliberate View+ViewModel+Store fusion:
  `bindValue` can only target fields **on the view type itself**
  (`mount.nim:289-297`), the inverse `set<Field>` writers are methods on the
  view (`uievents.nim:147-168`), and every doc example mirrors state into
  view fields. A separate model *can* observe/drive the view (ctx listeners +
  signals), but only hand-wired — the blessed path conflates model and view
  by convention.
- *Strength:* view-held state is plain data and echo-loop-free by
  construction — programmatic setters never re-emit (`vocab.nim:11-13`,
  verified in `tests/test_bindings.nim:94-114`).

### Control flow

- Handlers are free procs (not methods) resolved by identifier at the mount
  expansion site and invoked as `handler(self, ...)` — a presenter module can
  host them, but it always receives the whole view object and therefore
  compiles against the widget layer. No handler shape receives only data.
- `emits:` is a genuine controller seam, with two leaks: the event **type** is
  generated in the form's module (`uievents.nim:37-38`), so a model importing
  `LoginRequested` transitively imports the widget stack (ex13 avoids this by
  hand-defining events — undocumented); and generated events carry
  `senderId: int`, leaking view identity into model-facing payloads.
- *Strength:* `bindRequest` is a real control-plane extraction — replaceable
  validation providers with veto semantics, unit-testable as pure functions
  (`tests/test_validators.nim:50-60`).

### Decoupling quality & hazards

- The broker layer is the framework's best MVC asset (identity-in-route,
  ctx-as-value, safe-after-dispose, session sandboxing — all test-proven).
- Hazards: broker registrations hold strong refs (dispose-exactly-once or
  leak); user ctx listeners contaminate recycled ctx ids if not dropped
  first, with no runtime detection; `bindRequest` providers are global
  singletons registered on `DefaultBrokerContext` — another global-mutable
  channel requiring test hygiene (`test_bindings.nim:69`).

### Testability

- View without model: excellent (headless mount + real key routing + field
  assertions, `test_bindings.nim:39-79`). Control logic standalone: good.
- **Model without view: possible, unproven.** No test or example constructs a
  model object that doesn't see the view — even ex10's `connectFlow` takes
  the form as parameter while its comment claims "no widget procs".

### Consistency & guidance

- Nine sanctioned communication channels (slots, `bindTo`, `on:`, `emits:`,
  `action:`/commands, domain bus, `bindValue`, `bindRequest`, signals) across
  three context scopes (session, per-widget, default). Guidance exists
  (cookbook recipe 3, REFERENCE §6) but is *descriptive*, not *prescriptive*
  — it explains what each tier does, never which one a team should default
  to. **Risk that two teams ship incompatible architectures: medium-high.**
- The `emits:` default-vs-session ctx doc contradiction is the single most
  misleading line in the docs today.

### Pattern comparison

- Closest to classic OO MVC / TurboVision with an MVVM-flavored binding
  layer. Not Elm/MVU today — but a **strict unidirectional profile is
  genuinely buildable on existing primitives** (no-echo setters + semantic
  events out + signals in); what is missing is purely convention and a name.

## Consolidated prioritized recommendations

Concrete implementation plans for every item are in
[AUDIT-IMPLEMENTATION-PLAN.md](AUDIT-IMPLEMENTATION-PLAN.md) (WS numbers
below refer to its workstreams).

**Quick wins (docs only):**

1. Fix the doc/code contradictions — `emits:` ctx, dispose/ctx-recycling,
   test counts, Nim floor. *(WS1)*
2. Promote the lifecycle rules (dispose-exactly-once, remove-keeps-wiring,
   drop-listeners-before-dispose, ORC churn pattern) to a front-line chapter.
   *(WS1)*
3. Add a prescriptive Architecture chapter: one recommended default
   architecture, a decision table for the nine channels, an anti-pattern
   list, the context-scope matrix, and a named "strict MVU profile". *(WS2)*
4. Document the cross-module component pattern (exported factory proc).
   *(WS2)*
5. De-jargonize REFERENCE.md and fix examples-table drift. *(WS1)*

**Hardening (small code, high leverage):**

6. CI + tagged release + nimble registry publication + pinning guidance.
   *(WS3)*
7. Tighten the mount macros: validate names inside DSL strings with
   suggestions; hard-error the `on:` arity fallback; make the generic
   `createView` fallback safe; reject inherited `{.child.}` fields loudly.
   *(WS4)*
8. Host-integration hygiene: chain/restore prior signal handlers, remove
   TSTP/CONT handlers on deinit, `isatty` guard, SIGINT/SIGTERM terminal
   restore. *(WS5)*
9. Ship a public `illview/testing` module (off-screen buffer + snapshot
   helpers) with a cookbook recipe. *(WS6)*
10. Ship the chronicles router as a library API plus a one-page
    logos-delivery integration guide. *(WS7)*

**Strategic (design work):**

11. Decouple model from view in the blessed path: external-store binding,
    pre-declared event types for `uiEvents`, a standalone-model example and
    test, diagnostic-only `senderId`. *(WS8)*
12. A thin screen/navigator layer (named-view registry, activate-or-open,
    lazy mount, cached-screen contract) and instance-ctx reclamation. *(WS9)*
13. Open the extension surfaces: documented custom-widget DSL contract,
    custom `emits:` payloads, extensible theme tokens with derivation,
    declarative size-hint pragmas and a spacer. *(WS10)*
14. Formalize the render-target seam over `TerminalBuffer` — turning de-facto
    headless renderability into a supported remote/web-attach path. *(WS11)*
